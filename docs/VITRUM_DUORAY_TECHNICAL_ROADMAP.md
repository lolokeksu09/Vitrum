# Vitrum — техническая дорожная карта после сравнения с DUORAY-Mobile

**Статус:** реализация первого изолированного runtime-прототипа начата в PR #80; выполнение на ARM64-устройстве ещё не подтверждено.  
**Дата аудита:** 2026-11-07.  
**Область:** VPN-ядро, JSON-подписки и выбор серверов по типу сети.  
**Важно:** этот документ описывает направление и критерии будущих патчей. Он не утверждает, что перечисленные функции уже реализованы, и не разрешает менять сетевое поведение без отдельного этапа реализации и проверки.

## Текущий статус реализации — 2026-11-07

- PR #80: [feat: probe Xray runtime launch paths on ARM64](https://github.com/lolokeksu09/Vitrum/pull/80), draft.
- Добавлен `XrayRuntimeProbeTest` в `app/src/androidTest`: отдельно проверяет запуск встроенного Xray из `nativeLibraryDir` и запуск staged-копии через `/system/bin/linker64`.
- Добавлены AndroidX instrumentation dependencies и runner; `tools/build.sh tests` и release workflow компилируют `assembleDebugAndroidTest`.
- Добавлен отдельный ручной workflow [`xray-runtime-probe.yml`](../.github/workflows/xray-runtime-probe.yml): он проверяет unit tests и компиляцию instrumentation APK, сохраняет APK/отчёты и **не подписывает и не публикует релиз**. Запускать через Actions → `xray-runtime-probe`, указав `feat/xray-runtime-probe`.
- **Пока не проверено:** сборка instrumentation APK и фактический запуск на ARM64. До результата не выбирать linker как runtime, не реализовывать менеджер загрузки и не менять путь запуска в `RayVpnService`.
- Не менялись VPN/TUN/JNI runtime, Kill Switch, Vault, данные пользователя, package ID, versionCode/versionName и ключ подписи. Это тестовый каркас, а не готовый Xray Core Manager.

## 1. Цель

Развивать Vitrum как самостоятельный Android VPN-клиент, используя DUORAY-Mobile как технический ориентир. Улучшить управление версиями Xray, совместимость со сложными JSON-подписками и автоматический выбор серверов по сети, **не переписывая приложение на Rust/Slint и не заменяя существующую архитектуру**.

Основной принцип: заимствовать проверяемые технические идеи и совместимые сценарии, но не переносить вслепую реализацию другого приложения. Сначала фиксируются контракты и ограничения Vitrum, затем выполняются изолированные изменения с регрессионными тестами.

## 3. Архитектурные решения и границы

1. **Оставить текущую Android-архитектуру.** Kotlin, Jetpack Compose, RayVpnService, JNI и текущий Xray runtime остаются основой. Переход на Rust/Slint или полная замена app.rayclient не входят в этот план.
2. **Не подключать duoray-core как зависимость по умолчанию.** Текущая логика Vitrum написана самостоятельно; прямое подключение изменит стек, модель данных и границы совместимости. На данном этапе переносится только проверенная функциональная идея.
3. **Не копировать исходники или тексты DUORAY.** В AGENTS.md Vitrum уже зафиксирована политика самостоятельной реализации и документации. Сохранять её.
4. **Не менять package ID, ключ подписи, текущий формат хранилища и пользовательские данные без отдельного плана миграции.** Обычные обновления должны устанавливаться поверх существующего официального APK.
5. **Не ослаблять сетевую защиту ради совместимости.** Неизвестный или неподдерживаемый JSON не должен приводить к незаметному обходу VPN.
6. **Не смешивать этот план с UI overhaul.** Изменения экранов должны опираться на отдельный [VITRUM_UI_OVERHAUL_PLAN.md](VITRUM_UI_OVERHAUL_PLAN.md); сетевые патчи не должны превращаться в побочную перекраску интерфейса.

## 4. Приоритетные направления

### P0 — Управление версиями Xray-core

**Проблема.** Vitrum поставляет закреплённый Xray 26.3.27. В DUORAY-Mobile можно выбирать и устанавливать другие версии Xray с проверкой SHA-256. Это полезное направление, но способ запуска скачанного бинарного файла в DUORAY-Mobile отличается от текущего способа запуска Vitrum: DUORAY использует системный linker для бинарника из app-private storage, а Vitrum запускает libxray.so из nativeLibraryDir. Поэтому нельзя просто перенести downloader и считать архитектуру совместимой.

**Цель.** Ввести контролируемый жизненный цикл Xray: известная встроенная версия, поддерживаемые версии, проверенная установка, безопасный выбор и возможность отката.

**Предполагаемые файлы:**

- Brand.kt, tools/FETCH_BINARIES.sh, tools/binaries.sha256 — единый источник версии и контрольных сумм.
- Новый чистый модуль политики версий, например XrayCoreManager.kt / XrayCorePolicy.kt — только после подтверждения границ API.
- Native.kt, app/src/main/cpp/spawn.c, RayVpnService.kt, XrayOrphans.kt — интеграция запуска, остановки и очистки процессов.
- app/build.gradle.kts и упаковка JNI — только если доказанный вариант установки потребует изменений.

**Этапы:**

1. Зафиксировать текущий контракт запуска: путь к исполняемому файлу, ABI, передачу TUN FD, переменные окружения, код возврата, проверку PID, остановку и очистку orphan-процессов.
2. Провести небольшой технический прототип двух вариантов: запуск из Android nativeLibraryDir и запуск проверенного бинарного файла через системный linker. Проверить Android API 26 и актуальные версии Android на ARM64. Не принимать архитектурное решение только по коду DUORAY.
3. Определить метаданные версии: tag, ABI, размер, SHA-256, источник, статус совместимости и причина блокировки. Не доверять имени файла или версии внутри архива без проверки.
4. Реализовать ограниченную загрузку во временный файл, проверку digest, безопасную распаковку, проверку версии/ABI, тест конфигурации и атомарную активацию. При любой ошибке текущая рабочая версия должна остаться доступной.
5. Добавить явный выбор версии и откат. Не переключать ядро автоматически на непроверенный «самый новый» релиз.
6. Зафиксировать проверенную матрицу Xray-версий и использовать её в скрипте сборки, тестах и документации.

**Известный регрессионный случай.** v26.10.31 нельзя автоматически назначать рекомендуемой версией, пока не проверен исправленный upstream-релиз: в DUORAY PC зафиксирован SIGSEGV на XHTTP packet-up при TLS/mode=auto; разработчик временно использует v26.10.21. Этот случай должен стать отдельным тестовым профилем совместимости. Не считать v26.10.21 универсально рекомендуемой версией для всех будущих релизов.

**Критерии готовности:**

- Повреждённый, неподходящий по ABI или неподтверждённый бинарник не активируется.
- Неудачная загрузка, проверка или запуск не удаляет текущую рабочую версию.
- Переключение версии не создаёт второй Xray на том же TUN и не обходит kill switch.
- Работают старт, stop, reconnect, manual switch, failover и очистка orphan-процессов.
- Для каждой поддерживаемой версии проходят xray run -test на регрессионных конфигах; результат физического ARM64 теста фиксируется отдельно от JVM/CI тестов.

### P1 — Расширенная совместимость с JSON-подписками

**Проблема.** AutoSub.kt в текущем JSON-режиме Vitrum сознательно извлекает ограниченную часть Xray-конфигурации: серверные outbounds, balancers и burstObservatory. Входы, DNS и правила маршрутизации панели заменяются собственными. Это позволяет Vitrum применять свою политику безопасности, но может терять функции сложных конфигураций панели — цепочки, мосты, дополнительные DNS и связанные правила.

**Цель.** Расширить поддержку сложных конфигураций, не превращая импорт JSON в бесконтрольное выполнение любых настроек панели.

**Предполагаемые файлы:**

- AutoSub.kt — разбор, валидация и классификация конфигураций.
- AutoStore.kt — безопасное сохранение оригинального/нормализованного профиля.
- ConfigBuilder.kt — предсказуемое объединение конфигурации сервера с политикой Vitrum.
- HappRouting.kt, RuleCheck.kt, RuleOrder.kt — совместимость правил и приоритетов, если это подтверждено анализом.
- Новые fixture-файлы и тесты в app/src/test/java/app/rayclient/.

**Этапы:**

1. Составить матрицу полей JSON: поддерживается сейчас / может сохраняться / требует преобразования / запрещено или неизвестно. Отдельно учитывать outbounds, proxySettings/цепочки, balancers, observatory, routing, dns, inbounds, policy и транспортные параметры.
2. Подготовить обезличенные синтетические fixtures: одиночный outbound, несколько outbound, балансировщик, fallback, bridge/dialer chain, custom DNS, routing rules, неизвестные поля и конфликтующие/дублирующиеся теги.
3. Зафиксировать контракт владения настройками: какие элементы контролирует панель, какие — Vitrum, в каком порядке объединяются обязательные защитные правила, пользовательские правила и правила панели. Порядок должен быть детерминированным и покрытым тестами.
4. Сохранить текущий безопасный режим как совместимый вариант. Расширенный режим вводить отдельно, с понятным предупреждением о неподдерживаемых или отброшенных полях, а не молча подменять конфигурацию.
5. Проверять результат настоящим Xray соответствующей версии. Разбор JSON без запуска Xray не доказывает работоспособность конфигурации.

**Обязательные защитные условия:**

- Запрещены неожиданные локальные слушатели и открытые порты на loopback; служебные интерфейсы Vitrum остаются на приватных Unix-сокетах.
- Нельзя допускать, чтобы outbound, selector, fallback или цепочка незаметно выводили трафик в direct/мимо VPN.
- Проверять пустые, повторяющиеся и зарезервированные теги, неизвестные ссылки на outbound, слишком глубокий/большой JSON и неоднозначные ключи.
- Неизвестные поля не должны автоматически считаться безопасными. В расширенном режиме они либо сохраняются в безопасном контексте с явно определённой семантикой, либо отклоняются с объяснением.
- Секреты конфигураций и серверов продолжают храниться через существующие механизмы Vault/Android Keystore. Ошибка расшифровки или записи не должна затирать старые данные.

**Критерии готовности:**

- Для каждого поддерживаемого класса JSON есть fixture, позитивные и отрицательные тесты.
- Результат после объединения соответствует ожидаемому порядку routing rules.
- Реальный Xray принимает все позитивные fixtures и отклоняет ожидаемые негативные fixtures.
- Обновление подписки сохраняет пользовательский выбор, override и идентичность серверов по текущему контракту.
- Ни одна ошибка парсинга не приводит к пустому сохранению поверх ранее корректной подписки.

### P2 — Выбор сервера по типу сети и Wi-Fi SSID

**Текущее состояние.** В Scenarios.kt уже есть классификация Wi-Fi, мобильной сети, роуминга и открытой Wi-Fi, доверенные SSID и сценарии автоматизации VPN/профиля/kill switch. Поэтому не нужно создавать вторую независимую систему наблюдения за сетью. Требуется добавить политику выбора сервера поверх существующего механизма и определить её приоритеты.

**Цель.** Позволить назначить отдельный сервер для обычной Wi-Fi, мобильной сети и конкретной Wi-Fi сети; при смене сети Vitrum выбирает соответствующий сервер и безопасно переключает Xray, не теряя TUN.

**Предполагаемые файлы:**

- Scenarios.kt — использовать существующую классификацию и callback lifecycle.
- RayVpnService.kt — принять решение при реальном переходе сети и выполнить переключение через уже существующие безопасные механизмы.
- AppState.kt и модуль хранения — модель политики и миграция настроек.
- SettingsScreen.kt / соответствующие сетевые настройки — UI после согласования с UI overhaul.
- Новые чистые policy-классы и тесты в app/src/test/java/app/rayclient/.

**Предлагаемая модель приоритета:**

1. Точное совпадение SSID для активной Wi-Fi сети.
2. Сервер по умолчанию для Wi-Fi, если точного SSID нет или имя сети недоступно.
3. Отдельный сервер для мобильной сети; роуминг может иметь собственное правило либо явно наследовать мобильное.
4. Для открытой Wi-Fi сохраняются существующие сценарии безопасности. Открытая сеть не должна случайно наследовать политику доверенной Wi-Fi только из-за совпадения имени.

Окончательную семантику нужно закрепить до реализации. В частности, требуется определить, когда ручной выбор сервера временно переопределяет автоматическое правило и сбрасывается ли это переопределение при следующей смене типа сети.

**Защитные условия:**

- Смена сети обрабатывается по фактическому событию перехода, а не по каждому повторному callback.
- Отсутствующий/скрытый SSID не считается совпадением с сохранённой сетью.
- SSID не отправляется в аналитику или диагностические отчёты; настройки хранятся с учётом действующей модели защиты данных.
- Новый сервер не становится выбранным до успешной проверки нового маршрута — использовать существующие транзакционные механизмы ручного переключения/failover.
- При неудаче восстановить предыдущий маршрут либо оставить VPN заблокированным согласно текущему kill switch; не переводить трафик в прямой режим.
- Удалённые или отсутствующие серверы очищаются из сетевой политики без потери остальных настроек.

**Критерии готовности:**

- Unit-тесты покрывают Wi-Fi, mobile, roaming, open Wi-Fi, известный/неизвестный SSID, удалённый сервер, повторный callback и ручное переопределение.
- На физическом ARM64 устройстве проверены Wi-Fi → mobile → Wi-Fi, переход между двумя SSID и потеря сети во время переключения.
- Подключение и смена сервера не оставляют два Xray-процесса на одном TUN; kill switch проверен отдельно.
- После перезапуска приложения политика и выбранный сервер восстанавливаются корректно.

## 6. Общие проверки и выпускные gates

Каждый поведенческий патч должен иметь:

- unit/regression tests на новую политику и отрицательные сценарии;
- проверку синтаксиса и корректности Xray JSON настоящим Xray (xray run -test);
- проверку реального запуска и остановки Xray, PID и TUN FD;
- проверку STOP/START, reconnect, ручной смены, failover и kill switch;
- проверку миграции старых настроек и поведения при повреждённых/нечитаемых данных;
- обновлённые docs/HANDOFF.md, CHANGELOG.md и заметки релиза только тогда, когда соответствующее изменение действительно реализовано.

**CI не заменяет физическое устройство.** Для ARM64 runtime фиксировать модель устройства, Android/прошивку, commit SHA, версию Xray, APK SHA-256, сценарии, ожидаемый/фактический результат и redacted logcat. DNS/IPv4/IPv6 leak-free нельзя объявлять по одному HTTP-ответу служебного Xray-сокета.

Официальный APK выпускается через существующий workflow и действующий авторский ключ. Не использовать debug-fallback или временную подпись для обновления официальной установки. Package ID app.rayclient, сертификат и release-процесс сохраняются.

## 7. Не входит в этот план

- Переписывание Vitrum на Rust/Slint или полная интеграция duoray-core.
- Копирование исходников, UI или текстов DUORAY.
- Замена текущего VpnService, TUN pipeline или механизма хранения без отдельного технического обоснования.
- Изменение package ID, ключа подписи, существующих форматов подписок/backup без миграционного плана.
- Хотспот-прокси DUORAY-Mobile, 19 тем оформления и дополнительные функции, не относящиеся к трём приоритетам этого roadmap.
- Функции, требующие root, и попытки скрывать VPN от других приложений.
- Реализация полного UI overhaul: он ведётся отдельно.

## 8. Правило обновления документа

После каждого завершённого этапа:

1. Перепроверить фактические файлы и commit в main.
2. В этом документе изменить статус только того этапа, который прошёл соответствующие проверки.
3. Записать точные команды/CI run, commit SHA, Xray version и ограничения физического тестирования.
4. Не обозначать функцию готовой только на основании плана, успешной компиляции или unit-тестов.
